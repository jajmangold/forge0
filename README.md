# Forge0

Forge0 is a self-hosted development control plane built around Gitea. The
current MVP provides a FastAPI/HTMX portal for repositories and Actions,
project-aware LLM chat, SearXNG search, deterministic workflow primitives, and
an OpenCode configuration with reusable agent skills.

## Quick start

Requirements: Docker Engine with Compose v2, `curl`, and Python 3 (used by the
bootstrap script).

```bash
cp .env.example .env
# Add OPENCODE_API_KEY and replace the development passwords in .env.
docker compose up -d gitea
./setup.sh
```

The bootstrap creates the Gitea administrator and a fresh API token, stores the
runtime credentials in the ignored `.env.generated` file, and starts the core
stack. Open the portal at <http://localhost:3001>; Gitea is proxied at
<http://localhost:3001/gitea/>. All published ports bind to loopback by
default.

To start an optional service:

```bash
docker compose --env-file .env.generated --profile observability up -d wandb
docker compose --env-file .env.generated --profile optimization run --rm optuna
```

W&B and Optuna are experiments, not dependencies of the portal. Their profiles
keep the core stack small and prevent optional service failures from blocking
startup.

## Configuration

The portal needs `GITEA_API_TOKEN` (generated by `setup.sh`) and
`OPENCODE_API_KEY` for project chat. Important settings are listed in
[`.env.example`](.env.example). Auto-login is disabled by default; enable
`GITEA_AUTO_LOGIN=true` only for a trusted, single-user localhost deployment.

## Development

```bash
python3 -m venv .venv
. .venv/bin/activate
pip install -r portal/requirements.txt -r portal/requirements-dev.txt
pytest
ruff check .
pyright portal/app
docker compose config --quiet
```

The portal also exposes `/healthz` for liveness and `/readyz` for Gitea-backed
readiness. See [implementation status](docs/implementation-status.md) for the
boundary between the working MVP and researched roadmap items.

## Self-extension

Forge0 can turn a deliberately authorized issue in its own Gitea repository
into a verified draft pull request. Publish this repository to the configured
`FORGE0_SELF_REPO` (default `agent/forge0`), rerun `./setup.sh` to install the
webhook and labels, then create an issue containing a `## Acceptance Criteria`
section and add the `agent:ready` label. The portal's **Self-extension** page
shows persistent run state.

Each run uses a disposable clone and structured create/replace edits. It is
restricted to one repository and an operator-controlled path allowlist, with
file, diff, file-size, and LLM-token limits. It runs tests, Ruff, Pyright, and
byte-compilation, then asks a separate critic to approve the diff. The final
authority boundary is intentional: Forge0 pushes an `agent/` branch and opens
a draft PR, but it never merges or deploys its own work.

A signed Gitea webhook normally starts the run. An operator can also trigger
an eligible issue using the generated secret:

```bash
set -a; . ./.env.generated; set +a
curl -X POST \
  -H "X-Forge0-Operator-Token: $FORGE0_OPERATOR_TOKEN" \
  http://localhost:3001/api/dogfood/run/agent/forge0/ISSUE_NUMBER
```

## Repository map

- `portal/` — FastAPI portal, Gitea client, chat, agents, and tests
- `.opencode/` — OpenCode agents, permissions, and reusable skills
- `.gitea/` — issue/PR templates and Gitea Actions workflows
- `containers/` — development base images
- `docs/` — architecture, governance, workflows, and research
- `docker-compose.yaml` — local deployment

## Security notes

Do not commit `.env`, `.env.generated`, API keys, or the `data/` directory.
Change every example password before exposing Forge0 beyond localhost. The
initial commit contained `.env.generated`; rotate that Gitea token if this
repository has ever been shared.
